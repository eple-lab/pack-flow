# 09. 기능 목록

작성일: 2026-11-20 · 근거: 계획서 3 · 5절, [04 API 계약](04-api-contract.md), [work-units](work-units/README.md), [07 테스트](07-test-strategy.md)

기능 하나를 **화면 → API → DB 함수 → 작업 단위(WU) → 테스트 ID**로 한 줄에 따라간다. 사람과 에이전트 모두 "이 기능 어디까지 됐나"를 이 표로 판단한다.

- **상태** 칸은 eple이 매일 마감 통합 때 병합된 PR 기준으로 고친다(여럿이 고치면 충돌 — [06](06-work-plan.md) 1절). 값: `미착수` · `진행` · `완료(로컬)` · `완료(배포)` · `보류`
- 테스트 ID는 [07](07-test-strategy.md) 2절, 화면은 [10 화면 구성](10-screens.md)

## 2. MVP에서 하지 않는 것

| 기능 | 이유 · 대신 | 다음 |
|---|---|---|
| 품목 삭제, 거래처 마스터 화면 | 이력 · 거래가 품목을 참조, 거래처는 글자로만 | 고도화 |
| 차트 | 표로 대체 | 계획서 4절 '재고 · 출고 차트' |
| 배송 단계 (`배송중` · `배송완료`) | 출고까지만 | 계획서 4절 '배송 단계' |
| 사진 OCR 등록 | 일괄 등록으로 대체 | 계획서 4절 '사진 OCR 등록' |
| 연관 품목 제안, 추세 기반 입고 확대 | 발주 초안은 품절 임박 품목만 | 계획서 4절 '추세 기반 입고 확대' |
| 자금회수 · 정산, 구글 로그인, 카톡 연동 | 범위 밖 | 계획서 4절 |

전체 고도화 후보는 [계획서 4절](pack-flow-plan.md).

## 3. 용어 · 이름 규칙

에이전트가 같은 것을 다른 이름으로 부르지 않게 한다. 코드의 상수는 `src/types/erp.ts`가 원본이다.

| 구분 | 값 | 메모 |
|---|---|---|
| 구매 상태 | `발주완료` · `이동·통관중` · `입고완료` · `입고취소` · `품절` · `취소` | 한글 그대로 저장 · 표시. 영어 별칭을 만들지 않는다 |
| 판매 상태 | `주문접수` · `출고대기` · `출고완료` · `출고취소` · `주문취소` | 같음 |
| 재고 변동 사유 | `구매입고` · `실판매출고` · `입고취소` · `출고취소` · `재고조정` | `stock_logs.reason` |
| 사람이 읽는 번호 | 품목 `PRD-001`, 구매 `P-101`, 판매 `S-201` | 경로의 `{id}`는 uuid, 화면 표시는 번호 |
| 데이터 출처 | `form` · `bulk` · `agent` · `seed` | `source` 컬럼 |
| 오류 코드 | `PF_` + 대문자 (예 `PF_INSUFFICIENT_STOCK`) | [04](04-api-contract.md) 2절 |
| DB 함수 | `pf_` + 동사 (예 `pf_ship_sale`) | [03](03-data-model.md) 4절 |
| 테스트 ID | `T-S<Step>-<번호>`, `T-AUTH-<번호>`, `T-AI-<번호>`, `T-INV-<번호>` | 테스트 이름 맨 앞에 쓴다 (WU-45 결과표가 이걸로 묶음) |
| testid | `영역-대상-<번호>` (예 `btn-ship-S-201`, `alert-card-PRD-001`) | 목록은 [10](10-screens.md)과 각 WU |
| 기능 · 작업 · 결정 | `F-` 기능, `WU-` 작업 단위, `D-` · `P-` 결정, `Q-` 열린 질문 | 이 문서 · work-units · 02 · 08 |

## 4. 컨셉 자료와 다른 점 (참고)

`pack-flow-workspace/concept`의 의사결정 회의 자료(화면 시안 슬라이드 14 · 15 · 18 · 19)는 **참고만** 한다. 기준은 계획서와 이 문서들이다.

| 컨셉 자료 | MVP |
|---|---|
| 대시보드에 안전재고 점선 차트 | 표 (차트는 고도화) |
| 추천 수량 예시 `일평균 × (리드타임 + 여유) + 안전재고 − 현재고` | WU-32 공식과 같은 꼴. 여유일 상수를 둘지는 skygaul이 WU-32에서 정한다 |
| 발주 초안에 연관 품목 제안 | 하지 않음 |
| 일괄 등록 후 출고 건 → 배송 단계 연결 | 출고완료까지 (배송은 고도화) |
| 창고장 · 영업 · 입고 담당 역할 | 판매자 1인 (역할별 권한은 고도화) |
| 카톡 주문 · 보고 · 지시, 로컬 LLM 하이브리드 | 하지 않음 (발표의 '다음 단계') |
