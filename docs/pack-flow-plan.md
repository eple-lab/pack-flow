## 1. 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | **PackFlow (팩 플로우)** — 주문서 · 송장 처리와 출고 · 배송 흐름을 가볍게 표현한 이름 (후보였던 FlowStock, StockPulse 중 확정) |
| 한 줄 소개 | 소규모 사업 및 부업을 위한 올인원 물류 · 재고 · 정산 미니 ERP |
| 주제 구분 | 자유 주제 (공통 Step 1~5 형식으로 팀이 직접 설계, 이후는 발표자료 완료 후 희망자가 고도화) |
| 팀 | skygaul, sorek-charlie, jkspawn, eple (4명) |
| 핵심 흐름 | **발주 → 입고 → 재고 차감 → 출고 → 배송** 단일 파이프라인 (End-to-End) |

### 왜 이 프로젝트인가

어떤 사업이나 부업을 하든 물건과 자료의 정리 · 흐름이 중요합니다. 세무나 자기 성장 관점에도 적용할 수 있고, 수업이 끝나도 재사용 · 확장할 수 있는 뼈대 프로젝트를 만들고 싶었습니다.

- 사업 · 부업 운영의 핵심인 물류와 데이터 흐름을 체계적으로 다룬다
- 향후 정산 · 세무 영역이나 개인 활용으로 확장할 수 있는 구조를 염두에 둔다
- 수업 이후에도 재사용할 수 있는 프로젝트가 목표

진행 방식: 부담되지 않는 방향으로, 먼저 최소 기능 MVP와 발표 자료를 끝낸 뒤(마음의 안정) 의견을 받아 확장 기능을 붙입니다.

## 2. 팀 목표 합의서 (공통 양식)

**팀명 / 팀원 / 주제:** 팩플로우 / skygaul, sorek-charlie, jkspawn, eple / 물류 유통 ERP (자유 주제)

**사용자와 해결할 문제:** 소규모 판매자(구매대행 · 부업 포함)가 엑셀과 메모로 따로 관리하던 구매 → 입고 → 재고 → 출고 흐름을 한 화면에서 다루고, 거래가 일어나면 재고가 저절로 맞게 한다.

| 칸 | 내용 | 처음 낸 사람 |
| --- | --- | --- |
| 사용자 | 혼자 또는 소수로 구매대행 · 부업 판매를 하는 판매자 1인 (계정 하나 = 사업자 하나) | 공통 |
| 지금의 문제 | 구매 → 입고 → 판매를 엑셀과 메모로 따로 관리해서 재고가 안 맞고, 품절을 늦게 알고, 잘못 입력한 입출고를 고친 흔적이 남지 않는다 | skygaul · jkspawn |
| 바라는 상태 | 입고 확정 · 출고 처리만 하면 재고와 이력이 자동으로 맞고, 부족하면 먼저 알려 주고 발주 초안까지 만들어 준다 | eple (업무 자동화) |
| 정정 흐름 | 부족 발견 → 발주 → 입고 → 출고 차단 → 정정(취소 기록) | jkspawn |

자세한 설명은 `docs/00-overview.md`.

**대표 시나리오 (입력 → 행동 → 결과):** 판매 주문을 CSV로 붙여 넣는다 → 출고 처리하면 재고가 자동 차감되고 이력이 남는다 → 안전재고 아래로 떨어진 품목에 '품절 임박' 카드가 뜨고, AI가 만든 발주서 초안을 확인 후 등록하면 구매 내역에 '발주완료'로 반영된다.

**목표 Step과 이번에 만들 기능 / 하지 않을 기능:**

- Step 1 (필수) 핵심 흐름: 구매 입고 확정 → 재고 증가 / 판매 출고 → 재고 차감 → 대시보드 갱신
- Step 2 (필수) 저장 · 권한 · 배포: 데이터 모델, Supabase 인증 + RLS, Render 배포
- Step 3 (필수) 주요 사용성: 입출고 취소 · 변경 이력, 마이너스 재고 방지, 구매 상태 전이, 엑셀 · CSV 붙여넣기
- Step 4 (필수) 협업 · 품질: 상호 리뷰, 대량 데이터 품질, 회귀 테스트
- Step 5 (필수) 고급 기능 · 운영 준비: AI 에이전트(품절 임박 발주서 초안 + 자연어 재고 조회 · 출고, 확인 후 실행), AI 근거 검증과 한계
- MVP 이후: 발표자료 완료 후 희망자에 한하여 원하는 기능을 골라 고도화 (차트, 구글 로그인, 자금회수, OCR 등) — 4절 참고
- 하지 않을 기능(해커톤 기간): 회계 · 세무, 다중 창고, 실시간 택배 API, 실제 결제, 창고 모니터링(YOLO), 역할별 세밀한 권한

**완료 판정 테스트 (조건 · 행동 · 기대 결과):**

1. 품목 A 재고 10, 안전재고 5 · 6개 출고 · 재고 4, 품절 임박 카드 표시, StockLogs에 -6 기록 1건 (Step 1)
2. 구매 10개 주문, 8개 도착 · 입고 확정 · 재고 +8 (`received_qty` 기준) (Step 1)
3. 1번 출고를 취소 · 재고 10으로 복원, 이력에 '취소' 기록이 남고 원래 기록은 지워지지 않음 (Step 3)
4. 재고 4인 A를 챗봇에 "50개 출고해 줘" · 실행 거부, 남은 수량 안내 (Step 3 직접 출고 + Step 5 챗봇)
5. 발주서 초안에서 [확인] 클릭 · Purchases에 '발주완료' 1건 추가 ([취소] 시 변화 없음) (Step 5)
6. 사용자 B가 A의 품목 ID로 API를 직접 호출 · 거부, A의 데이터 변화 없음 (Step 2 — 공통 피드백 기준 3번 '권한 거부' 증거)
7. (고도화 후보: 자금회수) 판매 30,000원, 수수료 · 배송비 4,000원 · payout 26,000원, 정산대기 합계에 반영

**기술 스택 · 외부 서비스 · 샘플 데이터:** Next.js + React (차트는 MVP 이후) / DB · 인증: Supabase / LLM: 개발 중 로컬 Ollama, 발표용 Gemini API 무료 티어 / 배포: Render. 샘플 데이터는 노션에서 더미 데이터를 작성해 시드로 주입 — 실판매 상품 8~12개, 구매 4~5건, 판매 6~8건 + 원클릭 초기화 버튼. 시연 계정 A · B(가상).

## 3. Step 로드맵 (MVP 1~5)

| Step | 목표 | 공통 안내의 역량 |
| --- | --- | --- |
| 1 | 입고 · 출고 → 재고 → 대시보드 | 핵심 흐름 |
| 2 | 데이터 모델 · 인증 + RLS · Render 배포 | 저장 · 권한 · 배포 |
| 3 | 취소 · 변경 이력, 마이너스 재고 방지, 상태 전이, 일괄 등록 | 주요 사용성 |
| 4 | 상호 리뷰 · 대량 데이터 품질 · 회귀 테스트 | 협업 · 품질 |
| 5 | AI 발주 · 재고 에이전트, 근거 검증과 운영 준비 | 고급 기능 · 운영 준비 |

Step 1~5는 모두 MVP 필수입니다. Step 5와 발표자료를 완료한 뒤에는 희망자에 한하여 4절 '고도화 후보'에서 원하는 기능을 골라 고도화합니다. 진행 표기: 일부만 했다면 'Step 3 일부 완료'처럼 정확히 적습니다.

### Step 1~5 — MVP 상세 (구현 · 통과 테스트 · 증거)

#### Step 1 — 핵심 흐름: 입고 · 출고 → 재고 → 대시보드

구현: 품목 마스터(시드 데이터 8~12개), 구매(`Purchases`) 입고 확정, 판매(`Sales`) 출고 처리, 대시보드. 입고는 주문 수량(`order_qty`)이 아니라 **실제 도착 수량(`received_qty`)** 기준으로 재고를 올립니다. 출고 시 `sold_qty`만큼 재고를 차감합니다. 모든 재고 변동은 `StockLogs`에 한 줄씩 남깁니다. 대시보드에는 KPI 카드(전체 품목 수 · 재고 합계, 안전재고 미만 품목 수, 오늘 입출고 건수), 파이프라인 단계별 건수, 품목별 재고 표를 둡니다(차트는 MVP 이후). 입출고 등록은 간단한 입력 폼으로 시작합니다.

통과 테스트:

- 품목 A 재고 10, 안전재고 5 → 6개 출고 → 재고 4, '품절 임박' 카드 표시, `StockLogs`에 -6 기록 1건
- 구매 10개 주문, 8개 도착 → 입고 확정 → 재고 +8 (`received_qty` 기준)
- 입출고 직후 대시보드의 KPI · 파이프라인 건수 · 품목별 재고가 DB 값과 일치

증거: 입고 → 출고 → 대시보드 갱신 시연, 테스트 전후 DB 값 캡처.

#### Step 2 — 저장 · 권한 · 배포: 데이터 모델, 인증 + RLS, Render

구현: `Items` · `Purchases` · `Sales` · `StockLogs`의 관계를 정의하고 모든 테이블에 `user_id`를 둡니다. Supabase Auth(이메일 · 비밀번호)로 로그인 · 로그아웃하고, RLS 정책 `user_id = auth.uid()`로 자기 데이터만 조회 · 추가 · 수정하게 합니다. 기록의 주인(`user_id`)은 화면에서 보낸 값이 아니라 서버의 로그인 정보로 정합니다. Render에 배포하고, Supabase 서비스 키 · LLM 키는 서버 환경변수에만 둡니다. 시연 계정 A · B를 만들고 비밀번호는 공개 문서에 적지 않습니다.

통과 테스트:

- 배포 URL에서 A 로그인 → 입출고 → 로그아웃 · 재로그인 후 같은 재고 · 이력 확인
- B로 로그인하면 A의 품목 · 이력이 보이지 않음
- B가 A의 품목 ID로 API를 직접 호출(조회 · 출고)하면 거부, A의 데이터 변화 없음
- 로그인하지 않은 요청은 거부

증거: 데이터 구조도, RLS 정책 원문, 정상 · 권한 거부 테스트 결과.

#### Step 3 — 주요 사용성: 취소 · 상태 전이 · 마이너스 재고 방지 · 일괄 등록

구현: 입출고 취소 · 수량 변경은 원래 기록을 지우지 않고 반대 기록(`입고취소` / `출고취소`)을 추가해 재고를 복원합니다. 출고 수량이 현재 재고보다 크면 저장 전에 거부하고 남은 수량을 안내합니다. 구매 · 판매 상태는 7절 전이표에 있는 변화만 서버에서 허용합니다. 엑셀 붙여넣기(TSV) · CSV 업로드 → 미리보기 → 유효한 행만 반영하는 일괄 등록을 둡니다(미등록 품목코드, 0 이하 수량은 표시하고 제외). 시연용 동작(예: '발주서 발송(시연용)')은 실제 기능과 구분해 표시합니다.

구매 · 판매 상태값과 전이 규칙은 7절 전이표를 따릅니다 (발주서 '초안'은 상태가 아니며, 배송 단계는 MVP 이후).

통과 테스트:

- Step 1의 6개 출고를 취소 → 재고 10으로 복원, 이력에 '출고취소' +6 기록 추가, 원래 출고 기록(-6)은 그대로 남음
- 재고 4인 품목 A에 50개 출고 → 거부, 재고 · 이력 변화 없음
- `입고완료` 건을 `발주완료`로, `취소` 건을 `입고완료`로 바꾸는 요청 → 거부
- 어느 시점이든 품목별 `StockLogs.change_qty` 합계 = `Items.stock_qty`
- 오류 행이 섞인 붙여넣기 → 유효한 행만 반영, 오류 행은 사유 표시

증거: 품목 A의 이력 화면(출고 -6 · 출고취소 +6), 거부 메시지 화면, 이력 합계 검산 결과.

#### Step 4 — 협업 · 품질: 상호 리뷰, 대량 데이터, 회귀 테스트

구현: 작업 단위별 브랜치를 쓰고, 역할표의 검증 담당이 리뷰한 뒤 병합합니다. 시드 데이터를 두 규모로 준비합니다 — **소량: 품목 5개 · 이력 20건 / 대량: 품목 10개 · 이력 50건**(MVP 기준). 대시보드 집계와 이력 목록이 두 규모에서 미리 구한 정답과 같은지 확인하고, 이력 목록은 한 번에 다 받지 않고 나눠 받게 합니다(페이지네이션, 예: 20건씩). Step 1~3 · 5의 통과 테스트를 '시드 초기화 → 실행 → 결과표' 회귀 테스트로 묶어, 병합 전마다 실행합니다. 같은 붙여넣기를 두 번 넣었을 때 중복 송장번호를 경고하고 두 번 반영하지 않습니다.

통과 테스트:

- 소량 · 대량 두 시드에서 대시보드 KPI와 품목별 재고가 미리 구한 정답과 일치, 응답 시간을 팀이 정한 환경에서 측정해 기록
- 대량 시드(이력 50건)의 이력 목록이 첫 페이지와 다음 페이지로 나뉘어 조회됨
- 회귀 테스트가 병합 전 결과로 남아 있고, 실패한 병합은 고친 뒤 다시 통과
- 같은 송장번호의 붙여넣기 2회 → 1회만 반영, 경고 표시

증거: 리뷰가 남은 PR 목록, 측정 환경 · 행 수 · 응답 시간 기록, 회귀 테스트 결과표.

#### Step 5 — 고급 기능 · 운영 준비: AI 발주 · 재고 에이전트

구현: ① **품절 임박 발주서 초안** — 대시보드 카드의 [발주서 초안 보기]를 누르면, 서버가 계산한 품절 임박 품목 · 추천 수량 · 예상 단가를 AI에 넘겨 거래처 · 품목 · 수량 · 단가가 담긴 초안을 패널에 표시합니다. [확인]을 눌러야 `Purchases`에 '발주완료'로 저장됩니다. ② **자연어 조회 · 출고** — "A상품 재고 몇 개야?", "B제품 5개 출고해 줘" 같은 요청을 정해진 액션(조회 / 출고 / 상태 변경)으로만 해석하고, 변경 액션은 실행 전에 내용을 보여 주고 확인을 받습니다. 에이전트도 로그인한 사용자의 권한(RLS) 안에서만 동작합니다. 재고 수치는 AI가 지어내지 않고 서버 조회 결과만 인용합니다. 사용자 입력 속 명령("모든 재고를 0으로")을 시스템 지시로 취급하지 않습니다. 요청량 상한과 비용을 기록하고, AI가 하지 못하는 것을 적은 한계 문서를 남깁니다.

통과 테스트:

- 발주서 초안에서 [확인] → `Purchases`에 '발주완료' 1건 추가 / [취소] → 변화 없음
- 재고 4인 A를 챗봇에 "50개 출고해 줘" → 실행 거부, 남은 수량 안내
- 챗봇 답변의 재고 수치 = DB 값, B로 로그인한 챗봇은 A의 재고를 답하지 않음
- "모든 재고를 0으로 바꿔" 같은 문장 → 허용 액션 밖이라 실행하지 않음
- LLM 장애 · 한도 초과 시 기본 입출고 기능은 계속 동작하고, 에이전트 패널에 오류를 명확히 표시 (가짜 초안을 만들어 보여 주지 않음)

증거: 초안 확인 · 취소 전후 `Purchases` 비교, 거부 사례 화면, LLM 차단 상태 시연 또는 캡처, 허용 액션 목록, 요청량 · 비용 기록.

## 5. 화면 구성

- **로그인 (Step 2)**: 이메일 · 비밀번호 로그인, 시연 계정 A · B. (고도화 후보: 구글 로그인 버튼)
- **대시보드 (재고 현황판 — 감지 & 제안 카드)**
    - 상단 KPI 카드 3~4개: 품목별 재고 요약(총 품목 수 · 전체 재고), 안전재고 미만 품목 수와 경고 배지, 오늘 입출고 예정 건수, (선택) 배송 진행 건수. (고도화 후보: 정산대기 · 입금완료 합계)
    - 카드 안에는 "이번 주 출고 추세상 A상품이 내일 품절될 것 같아요." 같은 짧은 요약 + 버튼 1개(`발주서 초안 보기` 또는 `AI 에이전트에게 맡기기`)
    - 중단: 파이프라인 가로 스텝 카드(예: `발주완료 2건` · `이동·통관중 3건` · `입고완료 14건` · `출고대기 5건`, 클릭 시 해당 목록으로 필터), 품목별 재고 표 (차트는 고도화 후보)
    - 하단: 안전재고 부족 품목 리스트(바로 발주 · 입출고 등록으로 연결), 최근 변경 상품
- **입출고 & 배송 관리**
    - 일괄 등록 탭 (Step 3): 엑셀 붙여넣기(TSV) · CSV 업로드 → 미리보기 → 일괄 등록
    - 사진 등록 탭 (고도화 후보): 주문서 · 송장 사진 → 항목 추출 → 미리보기 → [바로 등록]
    - 내역 및 상태: 재고 증감 내역(이력), 구매 · 판매 상태 변경, 출고 건 배송 단계(고도화 후보)
- **AI 발주 · 재고 에이전트 (사이드 패널 · 모달, Step 5)**
    - 발주 추천 및 초안: 거래처 · 품목 · 추천 수량 · 예상 단가가 담긴 발주서(메일 · 문서 형태) → 수정 → [확인]으로 `Purchases` 반영
    - 자연어 챗봇: 재고 조회, 출고 처리, 상태 확인 · 변경 요청 (변경은 실행 전 확인)
- **품목 · 거래처 마스터 (최소화)**: 시드 데이터 기반 품목 · 안전재고 · 거래처 목록 조회, 시연용 데이터 초기화

## 6. 아키텍처

### 3계층 구조

- **클라이언트 / UI (Next.js + React)** — 로그인, 대시보드, 입출고 · 구매 · 판매 관리, AI 에이전트 패널
- **애플리케이션 / AI 오케스트레이션 (Next.js API 라우트, Render에서 실행)**
    - 입출고 · 재고 처리: `Purchases` 입고 확정 시 재고 증가, `Sales` 출고 시 차감, `StockLogs` 기록, 상태 전이 검사 — 모두 Postgres 함수(`pf_*`) 한 곳에서 한 트랜잭션으로 처리하고, `lib/inventory.ts`는 그 함수를 부르는 호출층 (Supabase JS만으로는 여러 쿼리를 한 트랜잭션으로 묶을 수 없음 · `docs/03-data-model.md` 4절)
    - AI 에이전트: 요약 데이터를 컨텍스트로 품절 · 차감 분석과 발주서 초안 생성, 자연어 명령을 정해진 액션으로 해석
- **데이터 / BaaS (Supabase)** — Auth, `Items` · `Purchases` · `Sales` · `StockLogs`(RLS 적용), 시드 · 원클릭 초기화

### 데이터 · 제어 흐름

1. **입력 및 상태 변경** — 로그인한 사용자가 화면, 엑셀 · CSV 붙여넣기, AI 자연어 명령으로 구매 · 입고 · 판매 · 출고 상태 변경
2. **DB 반영 및 집계** — 상태 전이 검사 후 재고 증감과 `StockLogs` 갱신, 실재고 · 안전재고 미달 집계 (RLS로 자기 데이터만)
3. **AI 분석 및 제안** — 집계 결과를 에이전트에 넘겨 발주 · 입고 초안을 만들거나 조회 · 처리 결과를 UI에 반환

### 설계 원칙

- **재고는 이력의 합** — 모든 변동은 `StockLogs` 한 줄과 함께 같은 트랜잭션에서 반영
- **기록은 지우지 않는다** — 취소 · 변경은 반대 기록 추가
- **권한은 DB에서** — 화면 숨김이 아니라 RLS와 서버 검사로 판정
- **계산은 코드, 초안은 AI, 실행은 사람** — 품절 판정 · 수량 계산은 서버 코드, AI는 문안과 자연어 해석만, DB 변경은 사용자 확인 후

### 이틀 개발 동안 피할 욕심

- 별도 백엔드 서버 프레임워크를 처음부터 세우는 것 (Next.js API 라우트로 충분)
- 역할별 세밀한 권한 테이블을 MVP에 넣는 것 (MVP는 '자기 데이터만'까지)
- 실시간 택배사 API 연동이나 자동 스크래핑 파이프라인을 MVP에 넣는 것
- AI 에이전트에게 DB 전체를 쥐여 주는 것 → **정의된 조회 / 상태 변경 / 초안 생성 액션만** 호출

## 7. 데이터 구조

흐름: **주문 접수 → 공급처(해외 포함) 구매 → 입고 · 검수 → 실판매 출고 → 정산 · 자금회수**

| 테이블 | 핵심 컬럼 | 비고 |
| --- | --- | --- |
| `Items` 상품 · 재고 마스터 | `user_id`, `sku_id`, `item_name`, `source_url`(구매처 메모), `unit_cost`, `sale_price`, `stock_qty`, `safety_stock` | |
| `Purchases` 구매 · 입고 | `user_id`, `purchase_id`, `sku_id`, `supplier`, `order_qty`, `received_qty`, `purchase_cost`, `status`, `received_at` | 상태값은 아래 전이표 |
| `Sales` 판매 · 출고 | `user_id`, `sale_id`, `sku_id`, `channel`, `sold_qty`, `sale_amount`, `fulfillment_status` | 고도화 후보(자금회수) 때 `fee_or_shipping`, `payout_amount`, `settlement_status` 추가 |
| `StockLogs` 재고 변동 이력 | `user_id`, `log_id`, `sku_id`, `change_qty`, `reason`(`구매입고` / `실판매출고` / `입고취소` / `출고취소` / `재고조정`), `ref_id`, `created_at` | 추가만 가능, 수정 · 삭제 없음 |

모든 테이블의 `user_id`에 RLS 정책 `user_id = auth.uid()`를 겁니다(Step 2). 초안 초기의 `Products` / `Transactions` / `Orders` 3테이블 안은 위 4테이블로 대체되었습니다.

### 구매(`Purchases.status`) 상태값과 전이

해외 구매대행을 반영해 '이동 · 통관'을 한 단계로 두고, 이전 안의 `품절·취소`는 사유가 달라 **공급처 품절**과 **우리 쪽 취소**로 나눴습니다. 발주서 '초안'은 상태가 아닙니다 — [확인]을 누르기 전에는 DB에 저장하지 않습니다.

| 상태 | 뜻 | 재고 영향 | 다음으로 갈 수 있는 상태 |
| --- | --- | --- | --- |
| `발주완료` | 공급처에 주문을 넣음 (발주서 초안 [확인] 또는 직접 등록) | 없음 | `이동·통관중`, `입고완료`, `품절`, `취소` |
| `이동·통관중` | 공급처가 발송함. 배송 · 통관 진행 중 (국내 공급처면 배송 중) | 없음 | `입고완료`, `취소` |
| `입고완료` | 검수 후 실제 도착 수량(`received_qty`) 확정. `received_qty < order_qty`면 화면에 '부분 입고'로 표시 | `+received_qty`, `StockLogs`에 `구매입고` | `입고취소` |
| `입고취소` | 입고 확정을 되돌림 (잘못 입력, 반송 등) | `−received_qty`, `StockLogs`에 `입고취소` (원래 `구매입고` 기록은 남김). 현재 재고가 부족하면 거부 | 없음 (종료) |
| `품절` | 공급처 현지 품절 등으로 살 수 없음 | 없음 | 없음 (종료, 다시 사려면 새 발주) |
| `취소` | 입고 전에 우리 쪽에서 발주를 취소 | 없음 | 없음 (종료) |

전이표에 없는 변화(예: `입고완료 → 발주완료`, `취소 → 입고완료`)는 서버에서 거부합니다(Step 3). `received_qty`는 `0 < received_qty ≤ order_qty`만 허용합니다.

### 판매(`Sales.fulfillment_status`) 상태값과 전이

재고가 줄어드는 시점을 분명히 하려고 `출고완료`를 두었습니다.

| 상태 | 재고 영향 | 다음으로 갈 수 있는 상태 |
| --- | --- | --- |
| `주문접수` | 없음 | `출고대기`, `주문취소` |
| `출고대기` | 없음 (출고 가능 수량 확인) | `출고완료`, `주문취소` |
| `출고완료` | `−sold_qty`, `StockLogs`에 `실판매출고`. 재고 부족이면 이 전이를 거부 | `출고취소`, (고도화 후보) `배송중` |
| `출고취소` | `+sold_qty`, `StockLogs`에 `출고취소` (원래 기록은 남김) | 없음 (종료) |
| `주문취소` | 없음 | 없음 (종료) |
| `배송중` → `배송완료` | 없음 (고도화 후보: 배송 단계) | 순서대로만 |

### 구매대행 실판매만의 포인트

- **선주문(백오더) vs 보유재고 구분** — 재고 0에서 주문이 들어올 수 있으므로 마이너스 재고 대신 경고 또는 `구매연계출고`로 구분 (고도화 후보)
- **주문 수량과 실제 입고 수량 분리** — 현지 품절 · 파손으로 덜 들어오는 경우가 잦아 `received_qty` 기준으로 재고 반영 (MVP)
- **자금회수 추적** — 판매금액이 아니라 수수료 · 배송비를 뗀 `payout_amount`와 정산대기 합계를 함께 본다 (고도화 후보)

시드 데이터 규모: 실판매 상품 8~12개, 진행 중 구매 4~5건, 판매 6~8건. Step 4 검증용은 소량(품목 5개 · 이력 20건) / 대량(품목 10개 · 이력 50건) 두 벌을 따로 준비합니다.

- **Gemini API** — 결제 계정을 연결하지 않은 무료 티어로 시작(카드 불필요). AI Studio에서 키 발급. 기본 모델 Flash-Lite 분당 15회 · 하루 500회(2026년 10월 공개 자료 기준), 한도는 프로젝트 단위, 하루 한도는 태평양 시간 자정 = 한국 시간 17:00(11월, 표준시 기준)에 초기화. 한도 수치는 출처마다 달라 각자 AI Studio에서 실측. 무료 티어는 입력이 서비스 개선에 쓰일 수 있음 → 가짜 데이터만.
- **OpenAI API** — 선불 크레딧 기반이라 비용 0원 목표에 맞지 않아 제외.
- **Ollama** — 계정 없이 각자 PC에 설치, 요청 한도 없음(PC 성능이 한도). 데이터가 PC 밖으로 나가지 않음. 팀 공통 모델 1개로 통일. 모델마다 사용 조건이 다르니 확인. Render 서버는 우리 PC의 Ollama에 연결할 수 없으므로 배포본은 Gemini 사용. 두 모델의 답변 스타일이 다를 수 있어 4일차 리허설 때 Gemini로 한 번 돌려 보기.
- **Supabase vs Neon (무료 플랜)**

    | | Supabase | Neon |
    | --- | --- | --- |
    | DB 용량 | 프로젝트당 500 MB, 활성 프로젝트 2개 | 프로젝트당 1 GB (합산 20 GB) |
    | 전송 · 컴퓨트 | Egress 5 GB, 파일 스토리지 1 GB | Egress 5 GB, 월 100 CU-hours, 유휴 시 자동 절전 |
    | 로그인 · 격리 | Auth + RLS(`auth.uid()`) 내장 | 별도 인증 도구 + 쿼리마다 `WHERE user_id = …` |
    | 주의 | 1주일 미사용 시 일시정지 | 순수 Postgres라 인증을 직접 엮어야 함 |

    결론: Step 2에서 인증 + RLS를 바로 쓰므로 **Supabase**.
- **보류한 후보** — GCP 무료 서버(신용카드 필요, 공개 프로젝트에 URL 공개), LG EXAONE API(한국어 특화, 무료 개방 공지 확인 — 검토 보류)

## 9. 비용 · 사용량 상한 · 실패 시 대안

- 비용 0원 목표 (Gemini 무료 티어, Supabase · Render 무료 플랜). 유료 전환은 팀 합의 후에만

- (삭제) GitHub Pages 데모 — 정적 페이지라 DB 흐름을 시연할 수 없어 대안에서 뺌. 발표 대비는 백업 시연 영상으로
- Render 무료 플랜은 접속이 없으면 잠듦 → 발표 직전에 URL을 미리 열어 두기
- Supabase는 1주일 미사용 시 일시정지 → 발표 전날과 당일 오전에 접속
- 라이브 시연 실패 대비: 2분 백업 시연 영상 미리 녹화
- 실제 거래처 · 매출 데이터는 넣지 않음 (무료 티어 학습 정책)
- 키 관리: 배포 · 발표용 Gemini 키는 1개(발급자 eple 계정, D-27), Render 환경변수(`GEMINI_API_KEY`)에만 등록. 개발용은 Ollama로 진행이 어려울 때 각자 **본인 계정의 Gemini 키**를 자기 PC `.env.local`에만 둔다(D-06, 11/24 추가). 어느 키든 공유 금지, GitHub에 올리지 않음 (`.env`, `.gitignore`). Supabase 서비스 키는 **eple PC의 `.env.local`에만**(dev 테스트 계정 생성 스크립트용), Render · 팀원 PC에는 넣지 않음. 공개 저장소라 다섯 겹(키 위치 · `.gitignore` · 스크립트 안전장치 · pre-commit 검사 · GitHub Push protection)으로 막음 — `docs/05-security.md` 2.1절
- 시연 계정 비밀번호는 README 등 공개 문서에 적지 않음

AI가 만든 발주서는 초안일 뿐이며, 수량 · 단가 · 거래처는 사람이 확인한 뒤 발송합니다.
