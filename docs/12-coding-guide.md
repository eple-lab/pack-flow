# 12. 코드 작성 가이드 (주석 · 이력 · 고친 기록)

작성일: 2026-11-20 · 근거: eple 결정(2026-11-20), task-hive(파일 머리 · 고친 기록 문서)와 healing-forest-trip(바꾼 줄 주석 · 이슈 연결) 비교

네 명이 각자 에이전트로 같은 저장소를 고친다. 나중에 코드를 연 사람(또는 에이전트)이 **이 파일이 무엇인지, 누가 만들고 누가 왜 고쳤는지, 이 줄이 왜 이런지**를 git을 뒤지지 않고 알 수 있게 한다.

| 무엇을 | 어디에 | 언제 |
|---|---|---|
| ① 파일 머리 (역할 · 근거 · 구역 · **이력**) | 파일 맨 위 | 파일을 만들 때, 그리고 고칠 때마다 이력 한 줄 |
| ② 함수 · 메서드 주석 | 내보내는 함수 · DB 함수 · 컴포넌트 위 | 만들 때, 동작이 바뀔 때 |
| ③ 바꾼 줄 주석 `[#이슈번호]` | 병합 뒤 고친 코드 덩어리 위 | 버그 · 요청 · 결정 변경으로 고칠 때 |
| ④ 고친 기록 | 이슈 본문(원본) → [13 고친 기록](13-fixes.md)(eple이 모음) | 고친 PR이 병합될 때 |
| ⑤ 커밋 · PR | 메시지 · 본문 | 매번 |

공통: **한국어로, "무엇"보다 "왜"를.** 코드만 봐도 아는 내용은 적지 않는다. 실명 · 이메일 · 키는 주석에도 적지 않는다(GitHub 아이디만).

## ① 파일 머리

### 모양 (TypeScript · TSX)

```ts
/**
 * 출고 · 출고 취소 API 라우트.
 *
 * 하는 일
 * 1. 입력을 saleShip 스키마로 검사한다(04 4.2).
 * 2. 사용자 JWT로 pf_ship_sale을 부른다. 재고 판정은 DB 함수가 한다(D-10).
 * 3. 함수 오류 코드를 04 4.4 문구로 바꾼다.
 *
 * 근거: docs/04-api-contract.md 3.4 · WU-41
 * 구역: eple (docs/06-work-plan.md 1절)
 *
 * 이력
 * 2026-11-23  eple     처음 작성 — 출고 · 출고 취소 라우트 (WU-41)
 * 2026-11-24  jkspawn  재고 부족이 500으로 나가던 매핑 수정 (#12)
 */
```

| 칸 | 규칙 |
|---|---|
| 첫 줄 | 이 파일이 무엇인지 한 문장 |
| 하는 일 | 흐름을 번호로 2~5줄. 지킬 규칙 · 하지 않는 것이 있으면 여기에(task-hive 방식) |
| 근거 | 문서 절 · WU · 결정 번호(D · P). 여럿이면 쉼표 |
| 구역 | 파일 주인(06 1절). 만든 사람과 지금 주인이 다를 수 있다 |
| **이력** | **첫 줄 = 최초 작성자**: `날짜  아이디  처음 작성 — 상세 (WU-xx)`. **그 아래 = 고친 사람**: `날짜  아이디  수정 이유 (#이슈 또는 WU-xx)`. 한 번 고칠 때 한 줄 |

### 이력 줄 규칙 (여러 명이 고칠 때)

- 날짜는 `YYYY-MM-DD`, 아이디는 GitHub 아이디(eple · sorek-charlie · jkspawn · skygaul). 칸은 공백 두 칸으로 맞춘다.
- **항상 맨 아래에 한 줄 추가**만 한다. 위 줄은 고치거나 지우지 않는다.
- 같은 PR 안에서 같은 파일을 여러 번 고쳤으면 이력은 한 줄로 합친다(커밋마다가 아니라 PR마다).
- 이유에는 **이슈 번호(#12)** 또는 **WU 번호**를 붙인다. 오타 · 서식처럼 동작이 안 바뀌는 수정은 이력에 적지 않는다.
- 병합 충돌이 이력 블록에서 나면 **두 줄 모두 남기고 날짜순으로** 정리한다(이력은 지우지 않는다).
- 에이전트가 고칠 때도 사람 아이디로 적는다(그 에이전트를 부린 사람). 에이전트 이름은 적지 않는다.

### SQL (마이그레이션 파일)

```sql
-- 재고 함수 1: 등록 · 입고 · 출고 (D-10, docs/03-data-model.md 4절)
--
-- 하는 일
-- 1. 모든 함수는 security definer + pf_require_user()로 주인을 확인한다.
-- 2. 재고와 stock_logs를 한 트랜잭션에서 바꾼다(재고는 이력의 합).
--
-- 근거: WU-21
-- 구역: sorek-charlie
--
-- 이력
-- 2026-11-23  sorek-charlie  처음 작성 — 생성 · 입고 · 출고 함수 (WU-21)
```

이미 적용된 마이그레이션은 고치지 않고 새 파일을 만든다(P-06). 그래서 SQL 파일의 이력은 보통 첫 줄 하나다. 새 파일의 근거 칸에 "이전 파일 `<ts>_inventory.sql`의 무엇을 바꾸는지"를 적는다.

### 머리를 달지 않는 파일

| 파일 | 대신 |
|---|---|
| JSON(시드 · 설정) — 주석을 못 단다 | 불러오는 쪽(`src/lib/seed/index.ts` 등) 머리에 설명 |
| 자동 생성 파일(lock, `.next` 등) | — |
| 문서(`.md`) | 문서 맨 위 "작성일 · 근거" 줄, 바뀐 내용은 문서의 변경 이력 표 |

## ② 함수 · 메서드 주석

**내보내는(export) 함수 · 컴포넌트 · 훅 · DB 함수**에는 반드시 단다. 파일 안에서만 쓰는 짧은 함수는 이름으로 뜻이 드러나면 생략해도 된다.

```ts
/**
 * 판매 한 건을 출고한다. 재고가 모자라면 출고하지 않는다.
 *
 * @param supabase 사용자 JWT 클라이언트 (서비스 키 클라이언트 금지 — P-03)
 * @param id 판매 uuid (화면 표시 번호 S-201이 아님)
 * @returns 바뀐 판매와 새 재고
 * @throws PF_INSUFFICIENT_STOCK · PF_INVALID_TRANSITION · PF_NOT_FOUND (04 2절)
 */
export async function shipSale(supabase: SupabaseClient, id: string) { … }
```

| 넣을 것 | 빼도 되는 것 |
|---|---|
| 한 줄 요약(무엇을 하는가) | 타입만 보면 아는 인자 설명 |
| 왜 이렇게 하는가(규칙 · 결정 번호) | 코드 줄을 말로 옮긴 것 |
| 던지는 오류 코드 | |
| 부작용(DB를 바꿈, LLM 호출, 상한 소모) | |

컴포넌트는 props와 testid를 적는다.

```tsx
/**
 * 품절 임박 카드. [발주서 초안 보기]를 누르면 에이전트 패널을 연다.
 * 숫자는 API 값 그대로 쓴다(화면에서 계산하지 않음 — T-S1-3).
 * testid: alert-card-<sku_id>, btn-draft-po-<sku_id>
 */
```

DB 함수는 위에 `--` 주석과 함께 `comment on function`도 단다(DB 대시보드에서 보이게).

```sql
-- 판매 한 건을 출고한다. 재고 부족이면 PF_INSUFFICIENT_STOCK, detail에 남은 수량.
create or replace function pf_ship_sale(p_id uuid) returns jsonb …;
comment on function pf_ship_sale(uuid) is '판매 출고: 재고 차감 + stock_logs 실판매출고 (D-10)';
```

애매한 줄에는 짧은 "왜" 주석을 단다(task-hive 방식).

```ts
// exclude: 화면이 stock_qty를 보내면 받지 않는다 — 재고는 DB 함수만 바꾼다(01 6절)
```

## ③ 바꾼 줄 주석 `[#이슈번호]`

healing-forest-trip의 `// [BUG-14] …` 방식을 쓰되, 번호는 **GitHub 이슈 번호**를 쓴다. 네 명이 동시에 써도 번호가 겹치지 않고 이슈로 바로 이어진다.

```ts
// [#12 bug] 재고 부족이 500으로 나가던 문제 → PF_INSUFFICIENT_STOCK을 409로 매핑 (jkspawn)
if (code === 'PF_INSUFFICIENT_STOCK') return 409;
```

```sql
-- [#15 decision] 수량 상한 100,000 → 50,000 (D-21, eple)
```

| 규칙 | 내용 |
|---|---|
| 언제 | **병합된 코드를 고칠 때만** — 버그(`bug`), 구역 요청(`request`), 결정 변경(`decision`). 처음 만드는 WU 작업에는 달지 않는다(파일 머리 이력에 WU가 있다) |
| 모양 | `// [#번호 종류] 무엇이 문제였나 → 어떻게 바꿨나 (아이디)` 한 줄. 종류는 이슈 라벨(11 1절) |
| 얼마나 | **바뀐 덩어리 하나에 한 줄.** 줄마다 달지 않는다 |
| 지우기 | 지우지 않는다. 같은 곳을 또 고치면 새 줄을 위에 더한다 |
| 함께 | 파일 머리 이력에도 한 줄(①), 이슈에 원인 · 수정 · 확인(④) |
| 이슈가 없을 때 | 고치기 전에 이슈를 먼저 만든다(11). 아주 급하면 `[#? bug]`로 두고 PR 전에 번호를 채운다 |

## ④ 고친 기록

- **원본은 이슈 본문**이다. 버그 양식(11 2절)의 "원인 · 수정 · 확인"을 고친 사람이 채운다. 고친 파일 · 줄도 적는다.
- [13 고친 기록](13-fixes.md)은 **eple이 매일 마감 때 이슈에서 모아** 적는다(task-hive `12-fixes.md` 양식). 한 파일을 여럿이 고치면 충돌하므로 팀원은 직접 고치지 않는다.
- 재발을 막는 테스트를 더했으면 테스트 이름에 이슈 번호를 넣는다: `it('T-S3-2 #12 재고 부족은 409', …)`.

## ⑤ 커밋 · PR

| 무엇 | 모양 |
|---|---|
| 기능 커밋 | `feat: 대시보드 KPI 카드 (WU-11)` |
| 고친 커밋 | `fix: 재고 부족 오류 코드 매핑 (#12)` |
| 테스트 · 문서 | `test: …`, `docs: …` |
| PR 본문 | `Refs #12` (`Closes`는 쓰지 않는다 — 확인 뒤 사람이 닫는다, 11 3절) |
| 병합 메시지 | 06 4절 양식(`Merge pull request #N from …` + WU · 리뷰 · 테스트 · 남은 것) |

## 리뷰 때 확인 (PR 체크리스트에 들어감)

- [ ] 새 파일에 머리(역할 · 근거 · 구역 · 이력 첫 줄)가 있다
- [ ] 고친 파일의 이력에 이번 PR 한 줄이 맨 아래에 있다
- [ ] 내보내는 함수 · 컴포넌트 · DB 함수에 주석이 있다(요약 · 오류 코드 · 부작용)
- [ ] 병합 뒤 고친 덩어리에 `[#번호 종류]` 주석이 있고, 이슈 번호가 맞다
- [ ] 주석에 실명 · 이메일 · 키 · 사용자 폴더 경로가 없다

## 두 프로젝트와 비교 (이 가이드를 정한 이유)

| 항목 | task-hive | healing-forest-trip | PackFlow |
