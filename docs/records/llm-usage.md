# LLM 사용량 · 상한 · 비용 기록

작성: skygaul · 2026-11-23 · WU-35 · 근거: [02 결정](../02-decisions.md) D-06 · P-09, [05 보안](../05-security.md) 4 · 7절, `src/lib/llm.ts`, `supabase/migrations/20261120100100_core_functions.sql`
갱신: skygaul · 2026-11-24 · 날짜별 호출 수(eple 조회) · 배포 지연(11/24 리허설) 채움

> 이 문서는 **호출이 어떻게 세어지는지, 상한이 얼마인지, 무엇이 비용을 만드는지**를 적고, 날짜별 호출 수와 지연은 실측 값으로 채운다. 호출 수 · 배포 지연은 11/24에 채웠고, **결제 확인(3절)** 은 키 발급자가 확인해야 해서 비어 있다.

## 1. 상한과 세는 방법

| 항목 | 값 | 근거 |
|---|---|---|
| 사용자당 하루 상한 | 30회 (`LLM_LIMIT_USER`, 기본 30) | 02 P-09, `env-server.ts` |
| 앱 전체 하루 상한 | 300회 (`LLM_LIMIT_GLOBAL`, 기본 300) | 02 P-09 |
| 하루의 기준 | **한국 시간 날짜** (`(now() at time zone 'Asia/Seoul')::date`) | `pf_llm_take` |
| 넘으면 | 429 `PF_QUOTA_EXCEEDED`(사용자 상한이면 `scope: user`, 전체면 `scope: global`) | `pf_llm_take` |
| 세는 곳 | `llm_usage(user_id, day, count)` 한 행이 사용자 · 날짜 한 쌍 | `schema.sql` |
| 올리는 시점 | **LLM을 부르기 직전**에 1 올린다. 그래서 제공자가 실패(503 · 시간 초과)해도 1회로 센다 | `llm.ts` `generate` 순서: 설정 확인 → 상한 확인 → 제공자 호출 |
| 올라가는 제공자 | `ollama` · `gemini` · `fake`가 모두 같다(제공자 구분 없음) | `llm.ts` |
| 호출 한 번이 되는 기능 | 발주서 초안 만들기 1회, 챗봇 메시지 1회. 후보가 없는 초안(LLM을 부르지 않음)과 `/execute` · `/confirm`은 세지 않는다 | `draft-po.ts`, `actions.ts` |

### 알아 둘 점
- **개발 모드에서는 패널을 열 때 초안 요청이 두 번 나간다**(개발 모드에서 같은 요청이 두 번 나가는 것을 브라우저에서 확인했고, React 엄격 모드 때문으로 보인다). 그래서 개발 중에는 초안 한 번에 2회가 올라간다. 배포(운영 빌드)에서는 1회다.
- 시험은 호출 상한을 쓰지 않도록 만들었다: 단위 시험은 `generate`를 가짜로 끼우고, `tests/api/agent-chat.test.ts`는 `@/lib/llm`을 가짜로 바꾼다. 반면 `tests/api/agent.test.ts`(T-AI-1)는 초안을 두 번 만들어 계정의 호출 수를 2 올린다.
- 사용자 상한은 계정마다 따로 센다. 발표 때 같은 계정으로 리허설 · 시연을 하면 합쳐서 30회다.
- 오류 문구(04 4.4)는 "한국 시간 오후 5시 이후 다시 쓸 수 있어요"라고 안내한다. 그런데 **우리 상한은 한국 시간 자정에 새로 시작**한다(`pf_llm_take`). 오후 5시는 Gemini 무료 할당량이 새로 시작하는 시각(태평양 시간 자정)에 맞춘 문구로 보이고, 우리 상한 문구와는 다르다. 사용자가 보는 안내와 실제 풀리는 시각이 어긋날 수 있다(문구는 eple 구역이라 고치지 않고 알린다).

## 2. 날짜별 호출 수

`llm_usage`에는 **읽기 정책이 없어서 사용자 계정으로는 읽을 수 없다**(`rls.sql`: "정책이 없는 테이블은 아무도 직접 읽지 못한다 — 의도한 동작"). 숫자는 Supabase SQL 편집기(프로젝트 소유자, eple)에서 아래로 뽑는다.

```sql
-- 날짜별 전체 호출 수와 가장 많이 쓴 사용자의 호출 수(사용자 ID는 문서에 적지 않는다)
select day, sum(count) as total, max(count) as max_per_user, count(*) as users
from public.llm_usage
group by day
order by day;
```

조회는 dev · demo 두 DB에서 했다(11/24 11:14 기준, eple). 위 쿼리의 `total`은 아래 표의 "전체 호출 수"다.

| DB | 날짜(한국 시간) | 전체 호출 수 | 사용자 최대 | 사용자 수 | 비고 |
|---|---|---|---|---|---|
| dev | 11/23 | 34 | 30 | 2 | 한 사용자가 사용자 상한 30에 닿음(챗봇 개발 · 시험, 추측) |
| dev | 11/24 | 5 | 3 | 2 | 조회 시각 기준 |
| demo | 11/23 | 3 | 3 | 1 | 밤의 400 실패 3번(실패한 호출도 센다) |
| demo | 11/24 | 4 | 4 | 1 | 초안 3 + 챗봇 503 1. 조회 뒤 리허설로 6회 더 올라감(아래) |

- **상한 대비**: 모든 날이 앱 전체 300회 · 사용자 30회 안이다. dev 11/23은 한 사용자가 정확히 30건이라 사용자 상한에 닿았다. 상한이 429로 막았는지는 이 표로는 알 수 없다(호출 수만 보인다).
- **실패한 호출도 센다**는 것이 실제로 확인됐다: demo 11/23의 3건은 모두 400 실패였고, 11/24의 4건에는 챗봇 503 1건이 들어 있다.
- **조회 뒤 늘어난 호출(SQL 재조회 전, 화면 기록)**: 11/24 배포 시연 계정에서 초안 1회 + 챗봇 5회(모두 성공)를 더 불렀다. 이 계정의 11/24 합계는 11:14 조회분 4건에 더해 약 10건으로 보이며 사용자 상한 30 안이다. 정확한 값은 최종 점검 때 위 쿼리로 다시 채운다.
- 사용자 ID · 이메일은 이 문서에 적지 않는다(날짜별 합계와 최대값만).

## 3. 비용

- **원칙**: 배포 · 발표는 Gemini 무료 티어, 개발은 각자 PC의 Ollama(D-06). 키 발급자는 팀이 정한 한 명이고 키는 서버 환경변수로만 읽는다(`env-server.ts`).
- **비용이 0원인 조건**: Gemini API 프로젝트에 **결제 계정이 연결되지 않은 상태**여야 무료 할당량만 쓴다. 결제를 연결하면 유료 단가가 적용되고 데이터 정책도 달라진다([ai-limits.md](ai-limits.md) 3절).
- **확인 방법(사람이 한다)**: Google AI Studio의 사용량 · 결제 화면에서 ① 결제 계정이 연결되지 않았는지, ② 사용한 호출 수 · 청구 금액이 0인지 캡처 없이 눈으로 확인하고 결과(날짜 · 확인한 사람)만 이 절에 적는다. 키가 보이는 화면은 캡처하지 않는다.
- **모델 · 무료 티어 가용성**은 Google 쪽 정책이 바뀔 수 있다. 사용 중인 모델 이름은 환경변수 `LLM_MODEL`이고, 모델별 무료 티어 여부는 [Gemini Developer API pricing](https://ai.google.dev/gemini-api/docs/pricing)에서 확인한다(발표 전 한 번).
- **한도 소진 대비**: 무료 티어 한도(분당 · 일일)에 걸리면 503 · 429가 난다. 그때는 초안은 표만, 챗봇은 오류 배너가 보이고 입출고는 그대로다. 최후 수단은 백업 시연 영상이다(05 7절 '무료 티어 가용성').

| 확인 항목 | 결과 | 확인한 사람 · 날짜 |
|---|---|---|
| 결제 계정 미연결(무료 할당량만 사용) | (키 발급자가 AI Studio에서 확인해 채움 — 11/24 현재 미확인) | |
| 청구 금액 0원 | (키 발급자가 AI Studio에서 확인해 채움 — 11/24 현재 미확인) | |

## 4. 지연 측정 메모 (로컬 개발 서버, skygaul, 2026-11-23)

표본이 적은 참고값이다. Gemini 줄은 개발 PC에서 Gemini 3.5 Flash Lite로 잰 값이다(발표 근거로 쓰려면 11/25 배포 URL에서 다시 잰다).

| 호출 | 제공자 | 표본 | 범위 | 비고 |
|---|---|---|---|---|
| 발주서 초안 문안 | Gemini(개발용: 3.5 Flash Lite) | 5 | 3.4 ~ 12.7초 | 서버 로그 `llm.ok`의 `ms` |
| 챗봇 해석 | Gemini(개발용: 3.5 Flash Lite) | 약 11 | 0.9 ~ 7.3초 | 대부분 1~3초 |
| 실패 | Gemini(개발용: 3.5 Flash Lite) | 2 | 2.6 · 3.6초 만에 503 | 서버 로그 `llm.failed`, 표 · 오류 배너는 정상 |
| 챗봇 해석 | Ollama(`qwen3.5:0.8b`) | 5 | 첫 호출 약 8.8초, 이후 0.25 ~ 0.49초 | 첫 호출은 모델 올리는 시간 |

- 시간 제한은 20초(`LLM_TIMEOUT_MS`)이고 넘으면 `PF_LLM_UNAVAILABLE`이다.
- 초안 문안이 챗봇 해석보다 느린 것은 응답 글자 수가 길기 때문으로 보인다(추측, 확인하지 않음).

### 배포 URL 리허설 (Gemini, skygaul 시연 계정, 2026-11-24)

배포 서비스의 `LLM_MODEL`은 `gemini-3.5-flash-lite`다(개발 PC와 같음, eple 확인). 아래 시간은 **브라우저에서 잰 응답 시간**(네트워크 포함)이라 서버 로그 `llm.ok`의 `ms`보다 길다. 같은 날 서버 로그의 초안 호출은 4.8초 · 4.3초였다(eple, #59).

| 호출 | 표본 | 응답 시간 | 결과 |
|---|---|---|---|
| 발주서 초안 | 4 | 2.5 · 1.4 · 12.6 · 1.6초 | 모두 `provider: gemini`, 200. 3번째만 크게 느렸다(원인 미확인) |
| 초안 [취소] · [발주 등록(확인)] | 각 1 | 확인 0.6초 | 취소는 구매 건수 그대로, 확인은 구매 +1(`source: agent`, 발주완료) — T-AI-1 |
| 챗봇 (5문장) | 5 | 1.0 · 1.9 · 4.2 · 1.3 · 2.7초 | 모두 성공. 재고 조회 · 부족 품목 · 출고 제안(실행 전) · 재고 초과 출고 거부(T-AI-2) · 모든 재고 0 거절(T-AI-4) |
| 챗봇 (실패) | 1 | 약 1.1~1.4초 만에 503 | `llm.failed`, `http_status: 503`. 직전 30초 안의 초안 3건은 같은 설정으로 성공했고, 다시 시도한 챗봇 5건은 모두 성공 |

- **503의 원인**: Gemini 서버가 처리하지 못한다고 답한 것이다. 같은 키 · 같은 모델 · 같은 설정으로 성공했으므로 설정 문제는 아니고, 무료 등급 모델의 일시 과부하로 보인다(추측, 응답 본문은 로그에 남기지 않아 정확한 사유 문구는 못 봤다).
- **재시도는 없다**: 503 · 429일 때 한 번 다시 시도하는 로직이 없어 사용자가 직접 다시 눌러야 한다. 재시도와 `usageMetadata` 로그 추가는 #59에서 검토한다.
- 개발 PC의 같은 날 값: 초안 2.0 · 9.7초(브라우저 기준), 챗봇 1.4초. 개발에서도 초안 지연의 편차가 컸다.
- 이 표본은 적다(초안 4 · 챗봇 6). 평균 · 최대로 말하지 않고 범위로만 쓴다.
