> 실패 → 원인 → 고침 → 재확인 순서로 적는다. 입력은 모두 가상 데이터이고, 키 · 계정 · 개인 정보는 적지 않는다.
> eple의 작업 방식: 관리 세션(Claude Code)이 단계마다 '다 됐다의 기준'과 기대 결과를 주고 구현은 하위 에이전트(Sonnet)에, 반복 실행 · 검산은 Haiku에 맡긴 뒤, 관리 세션이 기준 명령을 다시 돌리고 핵심 파일을 읽어 확인한다(D-34). 아래 세 사례는 모두 **기대 결과를 먼저 적은 시험이 AI의 실수를 잡은 경우**다.

## 사례 1 — 시험을 복제하다 기대값까지 바꿔 버렸다 (WU-41, 2026-11-23)

- 맡긴 것: 하위 에이전트(Sonnet)에게 조회 라우트 items · purchases · sales와 단위 시험을 맡겼다. "잘못된 status → 400 PF_VALIDATION, DB 호출 0회"를 구매 · 판매 둘 다 시험하라는 기준을 줬다.
- AI가 낸 것: 구매 시험(C-07)을 만든 뒤 sed로 판매 시험(C-12)을 복제했다. 이때 쿼리 이름 `status`를 DB 칸 이름 `fulfillment_status`로 바꾸는 치환이 시험의 **기대 field 값**에도 적용됐다.
- 문제: `npm run test:unit`에서 C-12가 실패했다. 기대 field는 `fulfillment_status`인데 실제 응답은 `status`였다.
- 원인: 코드는 맞았다. 판매 목록의 쿼리 파라미터는 계약(04 3.4)대로 `status`이고, DB 필터만 `fulfillment_status`를 쓴다. 복제할 때 바꿔야 할 곳(필터 칸)과 바꾸면 안 되는 곳(응답의 field)을 구분하지 않았다.
- 고친 것: 시험의 기대값만 `status`로 되돌렸다. 코드는 그대로 두었다.
- 다시 확인: C-10~C-14 통과, 전체 test:unit 571개 통과. 관리 세션이 같은 명령을 다시 돌려 확인했다.
- 배운 것: 시험이 실패하면 코드와 시험 중 **어느 쪽이 계약과 다른지**부터 본다. 기계적으로 복제한 시험은 기대값이 계약과 맞는지 다시 읽는다.

## 사례 2 — 가짜 클라이언트 대신 도우미 객체를 넘겨 모든 시험이 500이었다 (WU-43, 2026-11-23)

- 맡긴 것: 관리 세션(Claude)이 직접 `POST /api/seed` 라우트와 단위 시험 C-60~C-64를 썼다. 기대 결과를 먼저 적었다: demo → 200 + 건수, 모르는 dataset → 400, 미로그인 401, X-PF 없음 403, DB 오류 → 500(원문 없음).
- AI가 낸 것: 시험에서 `holder.client = fakeRpcDb(...)`로 가짜 Supabase를 넣었다.
- 문제: 5건이 모두 500이었다. 401 · 403을 기대한 시험까지 500이었으므로, 라우트 앞단에서 이미 예외가 난 것이었다.
- 원인: 서버 로그에 `"cause":"Cannot read properties of undefined (reading 'getClaims')"`가 찍혔다. 시험 도우미 `fakeRpcDb()`는 `{ client, rpcCalls, … }`를 돌려주는데, 클라이언트가 아니라 **도우미의 반환 객체 전체**를 넘겼다. 라우트 코드는 맞았다.
- 고친 것: `holder.client = db.client`로 시험만 고쳤다.
- 다시 확인: C-60~C-64 통과, 전체 test:unit 632개 통과. 뒤에 SeedError → 400 시험(C-65)을 더하면서, 라우트를 일부러 틀리게 바꿔 C-65만 실패하는 것도 확인했다(시험이 실제로 잡는지).
- 같은 날 비슷한 일: 하위 에이전트의 bulk 단위 시험에서 시험용 TSV의 마지막 칸이 비어 있어, 서버의 공백 정리가 끝 탭을 지우고 "열 개수 오류"가 났다(4건 실패). 시험 데이터에 값을 넣어 고쳤다.
- 배운 것: 기대가 서로 다른 시험(401 · 403 · 200)이 **모두 같은 값으로** 실패하면 코드보다 시험 준비(가짜 객체 · 데이터)를 먼저 의심한다. 로그의 원문 한 줄이 가장 빠른 단서다.

## 사례 3 — 테스트 ID 정규식이 접미사를 못 잡아 '기타'가 24줄 나왔다 (WU-45, 2026-11-23)

- 맡긴 것: 하위 에이전트(Sonnet)에게 회귀 실행기를 맡겼다. 테스트 이름 앞의 ID(`T-S1-1`, `C-01` 등)로 결과를 묶어 표를 만들고, ID가 없는 시험은 '기타'로 보내는 기준을 줬다.
- AI가 낸 것: ID 정규식을 `[A-Z0-9]` 조합으로만 썼다.
- 문제: 실제 dev에서 `npm run test:regression`을 돌리자 결과표의 '기타'가 24줄이었다. `T-AI-1a` · `T-VAL-4a`처럼 **소문자 접미사가 붙은 ID**를 ID로 인식하지 못했다. 단위 시험은 대문자 ID만 넣어 두어 통과했다.
- 원인: 팀 시험 이름에는 `T-AI-1a`처럼 같은 ID를 나눈 접미사가 쓰인다. 정규식과 시험 데이터가 이 규칙을 반영하지 않았다.
- 고친 것: 먼저 기대 시험(`T-AI-1a` → ID, `AI-driven` → ID 아님)을 추가해 **실패하는 것을 확인한 뒤** 정규식을 `^[A-Z]{1,4}(-[A-Za-z0-9]+)+`(숫자 포함, 뒤는 공백)로 고쳤다.
- 다시 확인: 결과표의 '기타' 0줄, `report.test.ts` 23개 통과, 일부러 실패시킨 시험(C-99)은 표에 '실패'로 나오고 종료 코드 1.
- 배운 것: 순수 함수의 단위 시험이 통과해도 **실제 데이터(팀의 시험 이름 전체)**로 한 번 돌려야 규칙의 빈틈이 보인다. 고칠 때는 실패하는 시험을 먼저 만든다.
