- Supabase RLS와 배포는 이전 프로젝트에서 해 봐서, 이번에는 AI 에이전트 기능을 직접 만들어 보고 싶었다.
- 첫날 팀 대화를 해 보니 4명이 각자 AI 도구로 함께 만들려면 누군가 프로젝트 구조를 먼저 잡아야 했다. 팀원들이 하고 싶은 파트를 맡을 수 있도록, 나는 에이전트 대신 골격(구조 · DB · 권한 · 배포)과 팀 운영을 맡기로 했다.

## 3. 느낀 점
팀장은 힘들다. 다들 어떤 프로젝트를 할지 고르던 1일차 점심시간에, 물류 ERP를 해 보고 싶어서 계획서 초안부터 썼다. 그때 뼈대와 PoC가 거의 다 나왔다.
구조까지 나눠서 하면 끝나지 않을 것 같아 골격과 문서를 먼저 만들었다. 2일차는 다들 에이전트가 돌고 있어 조용했지만, 병합이 몰린 3일차에는 총괄로서 말로 조율하느라 목이 쉬었다.
고생고생했지만, 발표 준비를 하는 지금은 뿌듯하다.

## 4. 에이전트를 다루면서 성장한 점
**한 줄: 에이전트와 함께 일하는 것(코웍)에 눈을 좀 떴다.**
- GitHub를 훨씬 넓게 쓰게 됐다. 전에는 md 문서를 만들어 에이전트가 읽고 작업하게 하는 방식이 중심이었고, 이슈는 디버깅에만 썼다. 이번에는 이슈와 PR을 개발 진행 관리 전체로 넓혔다.
- 처음으로 여러 사람의 에이전트와 한 프로젝트를 했다. 팀원들의 에이전트가 올린 이슈와 PR을 관리 세션과 함께 "올려도 되는지" 판단하고 최종 병합했다. 팀원이 디스코드에 에이전트 답변을 올리면 그 내용을 같이 분석하며 방향을 정했다.
- 관리 세션과 하위 에이전트로 일을 나누는 방식이 단단해졌다. 전에는 하위 에이전트가 하는 일이 보이지 않아 대화창이나 하위 세션에 직접 시키고 하나하나 검토했다. 바로 전 프로젝트부터 하위 에이전트를 쓰기 시작했고, 이번에 이 방식이 몸에 익었다.

## 5. 어려웠던 일
- 4일 일정을 한 번에 설계하기. 산출물과 발표 기준까지 머릿속에 그리면서, 여러 세션이 할 일이 서로 겹치지 않게, 보안과 권한까지 짧은 시간 안에 짜야 했다. 검색도 많이 했다.
- 3일차에 이슈 · PR · 병합을 말로 조율하기. 병합이 하루에 몰려서 총괄인 내가 계속 말로 순서를 맞췄고, 목이 쉬었다.

그래도 어려운 게 좋다. 한 번 해 봤으니 다음에 다시 하면 더 잘할 것 같다.

## 6. 힘들었지만 잘했다고 생각하는 일
- 이미 나와 있던 예시 프로젝트 대신 물류 ERP를 하겠다고 한 일. 다들 주제를 고르던 1일차 점심시간에 계획서 초안부터 썼고, 그때 문제 정의 · 데이터 구조 · 일정 · 범위 컷오프 · PoC까지 뼈대가 거의 다 나왔다.
- 팀장을 맡은 일.
  - 팀원이 에이전트에게 넘기기만 하면 되도록 기초 파일을 먼저 만들었다: 스키마 SQL · 화면 구성 html · 에이전트용 docs와 양식 · 이슈 처리 방법 · 라벨 · 훅 · `AGENTS.md`.
  - 3일차 기능 동결(14시) 전에 Step 1~5 기능을 범위를 줄이지 않고 모두 병합했고, 16:00 회귀에서 66 통과 · 0 실패를 냈다.

둘 다 앞에서는 푸념하듯 말했지만, 프로젝트가 큰 문제 없이 흘러가서인지 지금 돌아보면 다 좋아 보인다.

## 7. 아쉬웠던 일
- 커뮤니케이션 병목이 크지 않을 거라고 판단한 것.
  - 팀원마다 자기 에이전트와 일하다 보니, 에이전트의 답을 사람이 복사해 디스코드에 올리거나 말로 옮겨야 했다. 그 과정에서 내가 내용을 잘못 이해하는 일이 생겼다.
  - 슬랙을 쓰거나 디스코드에 MCP를 연결했으면 에이전트끼리 바로 주고받을 수 있었다. 하지만 그때는 그것까지 구성할 시간 여력이 없었다. 시간을 조금 더 들여서라도 해 둘걸, 하고 많이 아쉬웠다.
  - 다짐: 다음에 여러 사용자의 에이전트와 함께하는 프로젝트를 하게 되면, 커뮤니케이션 핫라인부터 꼭 만들어 두겠다.

크게 아쉽지 않은 것도 있다.
- AI 에이전트 파트를 직접 만들지 못한 것: 수업이 내년 4월까지라 조금 늦게 할 뿐, 앞으로 계속하게 될 일이다.
- 작업이 내 쪽에 몰린 것: 11/19 저녁부터 각오한 일이다.
- 영상 · 휴대폰 폭 같은 확인: 디스코드에서 풀었거나 후순위로 둔 일이다.
