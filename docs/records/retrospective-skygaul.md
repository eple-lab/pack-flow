## 1. 시작할 때 기대한 것
- 엑셀로 따로 적던 재고가 저절로 맞는 것을 만들어 보고 싶었다. 판매 주문을 붙여 넣고 출고하면 재고가 자동으로 줄고, 품절 임박 카드가 뜨고, AI가 쓴 발주서 초안을 확인한 뒤 등록하는 흐름이 1일차 합의서의 대표 시나리오였다.

## 2. 처음 생각과 달라진 점
| 처음 생각 | 실제로 겪은 일 |
|---|---|
| 허용된 액션만 쓰게 막으면 안전하다 | 실제 모델이 요청에 없는 구매 번호 `P-1`을 지어냈다(서버가 거부해서 피해는 없었다). 사용자가 말한 번호일 때만 제안하게 고쳤다 |
| Gemini는 빠르고 안정적일 것이다 | 응답이 1~5초로 흔들리고 가끔 503이 났다. 원인을 몰라 토큰 사용량 로그를 추가했다 |
| 구현하고 시험이 통과하면 쓸 수 있다 | 화면에서 챗봇을 여는 길이 없었고, AI는 "다른 사람 구역이라 요청이 필요하다"고 잘못 보고했다. 문서로 내 몫임을 확인한 뒤 패널 탭을 추가했다 |

## 3. 느낀 점
시험이 다 통과해도 안심하면 안 된다. 실제 모델과 실제 화면은 한 번은 직접 봐야 문제가 보였다.
AI가 "문제 없다 · 규칙을 지켰다"고 보고해도, 무엇을 기준으로 봤는지 사람이 되물어야 했다.

## 4. 에이전트를 다루면서 성장한 점
- 에이전트의 "구현 완료" 보고 뒤에 실제 Ollama · Gemini 호출과 브라우저 확인 단계를 두어, 가짜 시험이 못 보는 문제를 잡았다.
- AI의 "규칙을 지켰다" 보고를 코드와 대조하게 해서 규칙 위반 3건을 찾아냈다.

## 5. 어려웠던 일
- Gemini 응답이 1~5초로 흔들리고 가끔 503인데 원인을 알기 어려웠다. 토큰 로그를 넣었지만 생각 토큰은 없었고, 표본이 적어 "Gemini 쪽 편차로 본다"에서 멈췄다.
- 실제 모델이 틀린 곳(빈 응답, 번호 지어내기)은 가짜 시험이 모두 통과해서 실제 호출을 해 봐야 드러났다.

## 6. 힘들었지만 잘했다고 생각하는 일
- 실제 호출로 잡아 고친 일: 빈 응답은 `think:false`로, 지어낸 번호는 "사용자가 말한 번호일 때만 제안"으로, 챗봇 입구는 패널 탭 추가로 고치고 재확인했다. (근거: 사례 1 · 3 · 4, #51)
- 지연 원인 추적: Gemini 지연 진단을 이슈 #59로 올리고 토큰 사용량 로그를 직접 구현해 로그로 확인했다. (근거: #59 · #65)
- 리뷰로 버그 찾기: #57 리뷰에서 구글 시트 붙여넣기 때만 나오는 `열 개수 오류`를 찾아 이슈로 올렸고, 리뷰 10건을 승인까지 마쳤다. (근거: #57 · #60)

## 7. 아쉬웠던 일
- Ollama와 Gemini 비교가 얕았다. 팀 공통 모델 `qwen3.5:4b`로는 못 돌렸고, 비교 표본도 3~4건이었다.
- AI 보고 오류가 반복됐다. 커밋 메시지 이슈 번호 오기, 검사가 지워진 옛 파일을 읽은 거짓 통과, 영상 처음 평가에서 "문제 없음"이라고 한 것 모두 사람이 짚어서 고쳤다.

## 8. 배운 점
- 성장 면: AI의 "문제 없다 · 규칙을 지켰다" 보고를 그대로 받지 않고 기준을 되묻는다. 리뷰어일 때 사람이 실제로 쓰는 경로(구글 시트 붙여넣기)로 확인해 버그를 찾는다.
- 학습 면: 생각 모델은 응답 토큰을 생각에 다 써서 빈 응답이 나올 수 있다(`think:false`). 가짜 시험은 코드 흐름만 보장해서, 사용자가 닿는 경로(버튼 → 패널 → 화면)는 따로 따라가 봐야 한다.
