P-01 · P-08 · P-12 · P-19는 D-16~19와 같은 내용이다(계획서 반영 때 먼저 확정).

### 구조

| 번호 | 결정 | 이유 | 감수하는 것 |
|---|---|---|---|
| P-01 | 사용자 · 문제를 [00 개요](00-overview.md) 2절의 한 문장으로 통일 | 피드백 기준 1 "팀원 모두 같게 설명" | 계획서 2절 문장 정리 필요 |
| P-02 | **화면은 DB에 직접 쓰지 않는다.** 모든 변경은 `/api/**` → `pf_*` 함수. 조회도 API를 거친다 | 검증 · 오류 형식 · CSRF를 한곳에서. 챗봇 · 일괄 등록과 같은 입구 | API 라우트가 조금 늘어남 |
| P-03 | API 라우트는 **사용자 JWT가 실린** Supabase 클라이언트만 쓴다. 서비스 키는 시드 · 테스트 계정 생성 스크립트에서만 | 서비스 키는 RLS를 무시한다. 실수 하나로 남의 데이터가 열린다 | 관리 작업은 스크립트로 따로 |
| P-04 | 변경 함수는 `security definer` + 함수 첫 줄에서 `auth.uid()` 확인. 사용자에게는 테이블 SELECT와 품목 마스터 일부 컬럼만 권한을 준다 | "재고는 이력의 합", "기록은 지우지 않는다"를 DB가 강제 | 함수 작성 실수가 곧 보안 구멍 → 권한 테스트 필수([05](05-security.md)) |
| P-05 | 거래 테이블의 품목 참조는 `(user_id, sku_id)` 복합 외래키 | 남의 품목 코드를 참조하는 행이 DB에서 만들어지지 않는다 | 키가 두 컬럼 |
| P-06 | DB 변경은 `supabase/migrations/<타임스탬프>_<이름>.sql` 파일로만. 적용은 eple(통합 담당)이 Supabase CLI로 dev → demo 순서 | 두 프로젝트의 스키마가 같게 유지된다. SQL 편집기 수작업 금지 | sorek-charlie가 쓴 함수 파일도 eple이 적용 |
| P-07 | 남의 리소스 ID로 요청하면 403이 아니라 **404** | 그 ID가 존재하는지조차 알려 주지 않는다 | 디버깅 때 헷갈릴 수 있어 로그에는 이유를 남김 |
| P-12 | 앱은 저장소 루트에 둔다(`packflow-mvp/` 하위 폴더 없음) | Render · Actions 설정이 단순 | 계획서 8절 폴더 구조 수정 |
| P-13 | 팀원 공통 AI 코딩 규칙 파일 `AGENTS.md` 하나(Claude Code는 `CLAUDE.md`에서 이를 불러옴) | 각자 다른 도구를 써도 같은 규칙. healing-forest-trip 방식 | 도구별 차이는 각자 확인 |
| P-18 | 변경 요청(GET 외)은 헤더 `X-PF: 1` 필수 + 서버에서 `Origin` 확인 | 쿠키 세션의 CSRF 방어(task-hive 방식) | 테스트 코드도 헤더를 넣어야 함 |
