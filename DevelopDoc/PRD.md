# PackFlow PRD (제품 요구 문서)

작성일: 2026-11-23 · 근거: [docs/00-overview.md](../docs/00-overview.md), [계획서](../docs/pack-flow-plan.md) 2 · 3절 · 상태: **초안 — 11/25 최종 점검에서 갱신** · 11/24 밤 사실 대조 반영

원본은 `docs/`이고, 이 문서는 제출용 요약이다(D-12). 달라 보이면 `docs/`가 맞다.

## 1. 한 문장

소규모 판매자(구매대행 · 부업 포함)가 엑셀과 메모로 따로 관리하던 **구매 → 입고 → 재고 → 출고** 흐름을 한 화면에서 다루고, **거래가 일어나면 재고가 저절로 맞는** 미니 ERP.

## 2. 사용자와 문제

| 칸 | 내용 |
|---|---|
| 사용자 | 혼자 또는 소수로 구매대행 · 부업 판매를 하는 판매자 1인 (계정 하나 = 사업자 하나) |
| 지금의 문제 | 구매 → 입고 → 판매를 엑셀과 메모로 따로 관리해서 재고가 안 맞고, 품절을 늦게 알고, 잘못 입력한 입출고를 고친 흔적이 남지 않는다 |
| 바라는 상태 | 입고 확정 · 출고 처리만 하면 재고와 이력이 자동으로 맞고, 부족하면 먼저 알려 주고 발주 초안까지 만들어 준다 |
| 정정 흐름 | 부족 발견 → 발주 → 입고 → 출고 차단 → 정정(취소 기록) |

## 3. 대표 시나리오 (입력 → 행동 → 결과)

판매 주문을 CSV로 붙여 넣는다 → 출고 처리하면 재고가 자동 차감되고 이력이 남는다 → 안전재고 아래로 떨어진 품목에 '품절 임박' 카드가 뜨고, AI가 만든 발주서 초안을 확인 후 등록하면 구매 내역에 '발주완료'로 반영된다.

시연 순서: 로그인 → 시연 데이터 초기화(상단 바, F-25 — 본인 데이터만 시드로 되돌림) → (출고) → 품절 임박 카드 → 발주서 초안 확인 → 입고 → 취소 · 거부 사례 → B 계정 권한 거부. `demo` 시드에서는 출고를 입고보다 먼저 해야 카드가 뜬다([화면 구성](../docs/wireframes.html) 시연 절).

## 4. 목표 Step (모두 필수)

| Step | 목표 | 만드는 것 |
|---|---|---|
| 1 | 핵심 흐름 | 구매 입고 확정 → 재고 증가 / 판매 출고 → 재고 차감 → 대시보드 갱신 |
| 2 | 저장 · 권한 · 배포 | 데이터 모델, Supabase 인증 + RLS, Render 배포 |
| 3 | 주요 사용성 | 입출고 취소 · 변경 이력, 마이너스 재고 방지, 구매 상태 전이, 엑셀 · CSV 붙여넣기 |
| 4 | 협업 · 품질 | 상호 리뷰, 대량 데이터 품질, 회귀 테스트 |
| 5 | 고급 기능 · 운영 준비 | AI 에이전트(품절 임박 발주서 초안 + 자연어 재고 조회 · 출고, 확인 후 실행), AI 근거 검증과 한계 |

진행 표기는 일부만 했다면 'Step 3 일부 완료'처럼 정확히 적는다. MVP 이후 고도화 후보는 계획서 4절.

## 5. 핵심 기능

기능 목록 F-01~30은 [docs/09-features.md](../docs/09-features.md).

| 기능 | 내용 |
|---|---|
| 입고 · 출고 → 재고 | 입고 확정(실제 도착 수량 기준) · 출고 시 재고가 자동으로 바뀌고 이력이 한 줄씩 남음 |
| 취소 · 정정 | 원래 기록을 지우지 않고 반대 기록을 남겨 재고 복원. 재고보다 많은 출고는 거부 |
| 일괄 등록 | 엑셀 붙여넣기 · CSV → 미리보기 → 유효한 행만 반영, 중복 송장 차단 |
| 시연 데이터 초기화 | 상단 바 [시연 데이터 초기화]로 **본인 데이터만** 지우고 시드 3벌(`demo` · `small` · `large`) 중 하나를 다시 넣음(F-25) |
| 대시보드 | KPI · 단계별 건수 · 품목별 재고 · 품절 임박 카드 |
| AI 에이전트 | 품절 임박 발주서 초안(수치는 코드가 계산), 자연어 재고 조회 · 출고 — 확인 후에만 실행 |
| 권한 | 로그인한 사용자는 자기 데이터만 (DB의 행 단위 보안) |

## 6. 하지 않을 기능 (해커톤 기간)

회계 · 세무, 다중 창고, 실시간 택배 API, 실제 결제, 창고 모니터링(YOLO), 역할별 세밀한 권한.

**MVP 이후로 미룬 것**: 배송 단계(계획서 7절 전이표 기준 — 구매 · 판매 상태에 배송이 없음), 에이전트 패널 폭을 끌어서 조절하는 기능(이슈 #33, 기능 동결 뒤라 MVP 이후 후보로 둠).

**설계상 한계로 둔 것**(D-39): 일괄 등록에서 송장번호가 빈 행은 같은 내용을 다시 반영하면 중복으로 들어가고, 비고는 저장하지 않는다.

## 7. 완료 판정 테스트 (조건 · 행동 · 기대 결과)

| 번호 | 조건 · 행동 | 기대 결과 | Step |
|---|---|---|---|
| 1 | 품목 A 재고 10, 안전재고 5 · 6개 출고 | 재고 4, 품절 임박 카드 표시, 재고 이력에 -6 기록 1건 | 1 |
| 2 | 구매 10개 주문, 8개 도착 · 입고 확정 | 재고 +8 (`received_qty` 기준) | 1 |
| 3 | 1번 출고를 취소 | 재고 10으로 복원, 이력에 '취소' 기록이 남고 원래 기록은 지워지지 않음 | 3 |
| 4 | 재고 4인 A를 챗봇에 "50개 출고해 줘" | 실행 거부, 남은 수량 안내 | 3 · 5 |
| 5 | 발주서 초안에서 [확인] | 구매 내역에 '발주완료' 1건 추가 ([취소]면 변화 없음) | 5 |
| 6 | 사용자 B가 A의 품목 ID로 API 직접 호출 | 거부, A의 데이터 변화 없음 | 2 |

(계획서 2절의 7번 자금회수는 고도화 후보라 제외.) 각 테스트의 자동화 위치는 [docs/07-test-strategy.md](../docs/07-test-strategy.md).
